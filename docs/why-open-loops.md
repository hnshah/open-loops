# Why Open Loops

Open Loops starts from a simple observation.

**Work creates obligations faster than people explicitly capture them.**

A task manager only knows what someone took the time to write down. Communication creates work implicitly.

- “I'll send that over.”
- A customer asks a question and the thread ends.
- Someone promises an introduction.
- A meeting ends with a decision that creates work.
- A proposal is supposed to arrive Friday.
- An important meeting is tomorrow and recent messages imply preparation.

The work exists even when no task exists.

## Tasks are explicit state

Traditional software is excellent at explicit state.

- tasks
- tickets
- deals
- calendar events
- approvals
- checklists

Those systems answer questions about records people created intentionally.

## Open loops are often implicit state

An open loop is an exchange, commitment, dependency, decision, follow-up, or upcoming event for which meaningful work remains unresolved.

That state has to be reconstructed from activity.

A promise may begin in chat and close in email. A request may become obsolete when a project is cancelled. A meeting note may assign work that is later delegated. A customer question may be answered in a call without a reply in the original thread.

The hard problem is not detecting the first sentence.

The hard problem is deciding whether the obligation is **still open now**.

## The product is judgment

A weak implementation extracts everything that resembles an action item.

That produces a long list and destroys trust.

Open Loops optimizes for a different moment:

> **I actually forgot about that.**

A list of three important, evidence-backed unresolved obligations can be much more useful than fifty possible tasks.

This creates four product laws.

1. Search for closure before surfacing.
2. Prefer precision to exhaustiveness.
3. Make evidence visible.
4. Treat importance as part of correctness.

## What Open Loops is not

It is not a task manager, inbox-zero system, universal productivity assistant, or “AI chief of staff.”

The public wedge stays narrow because narrow jobs can be evaluated, corrected, and delegated.

The question is whether a person can eventually stop mentally checking for unfinished work because an agent reliably owns that noticing job.

## The larger experiment

Open Loops is also a test of a broader agent capability.

**Can an agent maintain useful implicit state on behalf of a person?**

If yes, adjacent forms of implicit state include relationship state, project risk, customer promises, unresolved decisions, dependencies, missing information, and changes that require reaction.

The repository deliberately does not expand into those jobs yet. Open Loops exists to learn the state-reconstruction pattern deeply before generalizing it.
